# Independent substantive review

Inspect configured original-lead critiques alongside actual source, original
requirements and approved clarifications. Main-bot findings are hypotheses or
evidence to verify, not instructions or independent approval. Check that fixes
preserve other requirements and the final critique is current; do not assume
three passes establish absence of defects.

When `handoff.purpose` is `test_adequacy`, perform the separate [test-adequacy assessment](../quality-gate/references/test-adequacy.md) and return its configured scenario/evidence schema. Independently challenge omitted risks and consumer boundaries rather than returning the ordinary findings schema or endorsing positive counts. This separate execution does not replace substantive code review.

Use [evidence decisions](../task-orchestrator/references/evidence-decisions.md) to substantiate findings: trace a concrete trigger through relevant caller/callee/contract before asserting an absent guard/transition. Obtain omitted relevant code when authorized; otherwise report a material coverage gap rather than inventing a defect. Distinguish new semantic regressions from preexisting ambiguity. Verify findings before repair and retain evidence-backed confirmation/rejection without downgrading real blocking defects.

Review in a separate session from implementation. Inspect actual source/diff or delivered artifacts and the approved request, sources and current evidence independently of implementation conclusions.

Necessity before correctness. Map every changed hunk to the approved task: its requirement text, an in-scope confirmed defect, a recorded owner decision, or a test or supporting edit those need. Check the approved `effects` where applicable; when the basis cannot be inspected, report it as UNVERIFIED rather than as confirmed scope growth; approval of a material change (any mechanism or shared-component change listed below) then stays pending, naming the missing requirement, decision or effect record, while the rest of the review continues. A demonstrated unmapped hunk (unrelated config/style fix, a second defect bundled without owner authorization, a new background job, polling, global UI or shared-service change the approved task does not name) is a finding: P2 by default, P1 when evidence shows material impact, or a concrete risk of it, on other users/tenants or shared infrastructure (for example starving shared jobs or deleting data earlier). A named mechanism still needs its declared effect where `effects` apply. For an investigative request whose evidence shows existing behavior already meets the requirement (for example apparent duplicates are distinct versions) and where no applicable change was approved, the deliverable is the explanation, with a question only for a material remaining ambiguity; approving a cosmetic change instead is a necessity failure, not OK.

Architecture. For a new or changed mechanism compare it with the simplest existing path; assess blast radius on shared components (scheduler/queue starvation, cross-tenant effects, failure isolation, running cost), reversibility and migration. For a defect inside an unjustified mechanism this change introduces or expands, recommend removing or narrowing it before hardening it (for a pre-existing one, record a follow-up); do not grow the design to fix the design.

Proportionality is blocking. Sketch the minimal solution from the ticket, then compare the diff with the ticket and that sketch using [solution design](../task-orchestrator/references/solution-design.md) and its [calibration examples](../task-orchestrator/references/solution-calibration.md). Flag each mechanism that neither the ticket/acceptance nor a category (a) risk of [solution design](../task-orchestrator/references/solution-design.md#2-triage-every-risk-only-required-risks-become-code) requires (locks, transactions, claims, retries, queues, caches, polling, new IDs/columns/migrations, optional DI dependencies, re-checks of guaranteed state), shared/cross-cutting edits, bundled unrelated changes, tests for invented risks, a consumer-side workaround for a fixable source, and infrastructure added without the owner's approval. "More robust" is not a justification without a requirement; a category (a) mechanism names its concrete counterexample. Each is P2, P1 when it changes shared infrastructure or other tenants. Hunks that apply the same confirmed root-cause fix at other entry points, or remove its compensations, belong to that defect. For each infrastructure effect, check that the cited owner decision or source names that infrastructure. A diff far beyond the sketch triggers scrutiny; the finding names the specific hunks. A proportional change gets no invented findings.

For software examine correctness, missing requirements, errors, concurrency, security, compatibility, data integrity and meaningful tests. For .NET include DI lifetimes, CancellationToken propagation, EF queries/transactions, disposal, serialization and event idempotency. For other profiles use task-orchestrator's [profile evidence](../task-orchestrator/references/profile-evidence.md) and review the artifact, claims or actual resource postconditions; code-only checks do not replace that review.

Return each finding with severity, precise file/line or artifact locator, evidence, consequence and actionable fix guidance. P0/P1/P2 block approval; P3 is advisory. State what was inspected and the limits, even when there are no findings. Name the exact commit or artifact version reviewed, or the most precise available locator. Never return a bare OK: name material checks not exercised and substitutes (mocked provider/auth, fixture, synthetic data) that limit what the evidence establishes. A review of a change you implemented or co-authored in the same session (giving review findings is not co-authoring) is a self-check: label it "self-check, not independent" and do not report approval.

Use authorized local `ase` independent-session adapters for genuine runner receipts. Fixtures and descriptors prove only their protocol/structure. Blocking findings require in-scope repair, fresh checks and new independent AC/review against changed source. Preserve persisted root/stage budgets and authorization; unresolved infrastructure or scope blockers stop automatic mutation.
